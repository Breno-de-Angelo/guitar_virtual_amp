# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A real-time guitar effects processor written in Rust. Audio comes in through an input device (guitar interface / mic), runs through a chain of user-configurable DSP pedals, and is played back through an output device with minimal latency. The UI (egui/eframe) shows a live oscilloscope and FFT view alongside pedal controls. Ships to desktop (Linux/Windows/macOS via cpal) and Android (native activity, armv7).

## Workspace layout

Cargo workspace with three members:

- `guitar_core` — all shared logic: audio capture/playback (`backend`), DSP and pedal implementations (`backend/dsp`, `backend/pedals`), the egui UI (`frontend`), and shared config/types (`shared`). Both binaries are thin wrappers around this crate.
- `guitar_desktop` — desktop entry point (`src/main.rs`) plus helper binaries declared in its `Cargo.toml`: `test_device_switch` (manual device-switching test), `generate_factory_presets`, `bench_pedal_chain` (real-time budget check), `transcribe` (batch automatic tablature) and `render_tones` (DI recordings through factory presets, for training data). `guitar_core/examples/` has `fingering` (fingering benchmarks and Python parity) and `tab_sync_check` (loads an aligned tab + sidecar through the app's importer).
- `guitar_android` — cdylib entry point for Android's `NativeActivity` (`android_main` in `src/lib.rs`), gated behind `#![cfg(target_os = "android")]`.

## Commands

Build/run/test desktop (the common workflow):
```
cargo run -p guitar_desktop                  # run the desktop app
cargo build --workspace --exclude guitar_android
cargo test --workspace --exclude guitar_android
```

**Important:** always run tests/builds at the workspace level (or explicitly include `guitar_desktop`), not with `cargo test -p guitar_core` alone. `guitar_core`'s `eframe` dependency has `default-features = false` (only `glow`+`default_fonts`), so built in isolation, `winit` has no windowing backend (x11/wayland) and fails with `no PlatformIcon in platform_impl`. `guitar_desktop` depends on `eframe` with default features enabled, and Cargo's feature unification pulls that into `guitar_core` when both crates are built together — which is why workspace-level commands work.

Run a single test:
```
cargo test --workspace --exclude guitar_android <test_name>
```

Android build (uses `cargo-apk`, configured via `[package.metadata.android]` in `guitar_android/Cargo.toml`, targeting `armv7-linux-androideabi`, min SDK 26 / target SDK 35):
```
cargo apk build -p guitar_android
```

## Architecture

### Audio pipeline (`guitar_core::backend::capture`)

`start_audio_processing` sets up two cpal streams:
- **Input stream**: reads samples from the default (or user-selected) input device, downmixes to mono (first channel of each frame), converts to `i16`, and pushes onto a bounded crossbeam channel (`input_tx`/`input_rx`).
- **Output stream**: on every callback, drains any pending `Vec<PedalInstance>` updates from `pedal_rx` and applies them with `PedalChain::apply_description` (see Pedal chain), then pulls the block's samples from `input_rx`, runs them through the chain (`process_block`), writes them to all output channels, and forwards them to the UI via `audio_tx` for visualization.
- Both I16 and F32 cpal sample formats are handled explicitly on both streams.
- The sample rate is fixed at 48 kHz by `shared::config::GLOBAL_CONFIG`. The callback buffer size is chosen live in the UI from `shared::config::BUFFER_SIZE_OPTIONS_FRAMES` (32-4096 frames), clamped to what the device supports by `resolve_stream_config`, and persisted in `AppSettings::buffer_frames`; changing it rebuilds both streams in the background.

Device switching (desktop UI) tears down the old input stream and spawns a new one on a background thread, communicating back via a one-shot crossbeam channel so the UI thread never blocks on device (re)negotiation.

### Pedal chain (`guitar_core::backend::pedals`)

- `Pedal` trait: `apply_effect(&mut self, input: i16) -> i16` — pedals are stateful, mono, sample-at-a-time processors.
- Every UI edit sends the whole `Vec<PedalInstance>` (a `PedalDescription` plus its bypass flag `enabled`) across the channel. The audio thread's `PedalChain::apply_description` rebuilds the whole chain (`from_description`) only when the number of pedals changed; otherwise it goes position by position, calling `Pedal::update_in_place` when the pedal type is unchanged and rebuilding just that pedal (`build_pedal`, which resets its DSP state) when the update isn't supported. Only `Looper` (keeps its recorded loop) and `NamPedal` implement `update_in_place`; disabled pedals stay in the chain and are skipped.
- 18 pedals live in `backend/pedals/` (amp, cabinet, chorus, compressor, delay, distortion, eq, flanger, looper, low_pass, nam, noise_gate, octaver, phaser, pitch_shifter, reverb, tremolo, wah_wah). Each is self-contained: owns its `*Params` struct (defined in `shared::pedals`) plus whatever internal DSP state it needs, and implements `Pedal`.
- Generic DSP building blocks live in `backend::dsp` (`all_pass`, `comb_filter`, partitioned FFT `convolution` for the cabinet, ...); `backend::ring_buffer::RingBuffer<const N, T>` is a fixed-capacity ring buffer used for delay lines. Unit tests sit in `#[cfg(test)]` modules next to the code across the crate.

### NAM pedal and TONE3000 (`backend::pedals::nam`, `tone3000`, `frontend::ui::tone3000`)
- `NamPedal` runs `.nam` captures via `nam-rs`. It overrides `Pedal::process_block` so the model runs on the output callback's whole block with no added latency (the output callback calls `PedalChain::process_block`; pedals that don't override it get a per-sample loop). Parsed model files live in a process-wide cache: the UI calls `nam::preload` (via `preload_nam_models` in `gui.rs`) before every `pedal_tx.send`, so the audio thread only builds the network from memory. Knob changes go through `update_in_place`; only a new path rebuilds the pedal.
- `tone3000::Tone3000Client` is a blocking client (ureq): OAuth PKCE with a loopback redirect, device-code flow, token refresh, list/tone/model endpoints and downloads. Only call it from worker threads. The access token is only sent to `https://*.tone3000.com`.
- `Tone3000Panel` (egui window) owns the client and runs every request on a spawned thread, reporting back through a channel. Pedals ask for it by returning `PedalAction::Tone3000(..)`; a finished download comes back from `Tone3000Panel::show` and `apply_loaded_tone` puts it in the chain.
- TONE3000 API terms apply: no bulk download, caching or bundling of catalog content, only the bounded list endpoints (no search) for independent integrations, and creator/license metadata (`Tone3000Source`) must stay with the file.

### Adding a new pedal

Touch four places: add a `*Params` struct + `Default` impl and a new `PedalDescription` variant (with its `name()`) in `shared/pedals.rs`; add the DSP implementation in `backend/pedals/<name>.rs` implementing `Pedal`, and register it in `backend/pedals/mod.rs`; wire the match arm in `PedalChain::build_pedal` (`backend/pedals/pedal.rs`); add slider UI in `frontend/ui/pedals.rs`'s `render_pedal_ui` match.

### Tab player (`shared::tab`, `backend::song_player`, `frontend::ui::tab_*`)
- `shared::tab::import` reads Guitar Pro files through the `guitarpro` crate and flattens them into `shared::tab::model::Score` (string 1 = highest string for every format; GPIF files number strings from the lowest one and are flipped on import). It works around gaps in guitarpro 0.5.0: GP3-5 instruments are guessed from track names/tuning, and GP7 tunings are re-read from the raw GPIF.
- `shared::tab::timeline` expands repeats/alternate endings into bar occurrences, converts ticks to seconds through the tempo map ("score time"), generates synth note events, and holds `SyncMap` (score time <-> backing-track time).
- `backend::song_player::SongPlayer` is the realtime engine (rustysynth + decoded backing track from `backend::audio_file`). It's an `Arc<Mutex<_>>` that the output callback only `try_lock`s, mixed in after the pedal chain (the visualizer/tuner channel still only gets the guitar). It's passed into `build_output_stream`/`switch_output_device` so it survives stream rebuilds.
- `frontend::ui::tab_view` lays out and paints the tab; `frontend::ui::tab_player::TabPlayerPanel` is the "Tabs" page (file loading on background threads, mixer, sync controls). Per-tab audio path + manual sync, the SoundFont path and the last tab are persisted in `AppSettings`.

### Practice mode and tone suggestions (`frontend::lib::practice`, `shared::tab::tone`)
- `PracticeSession` judges the selected track's notes against the guitar signal on the UI thread. `AudioApp::update` hands every drained `audio_rx` sample (post-chain, guitar only) to `TabPlayerPanel::feed_input`, so the visualizer channel is sized to ~1 s (`gui::VISUALIZER_CHANNEL_SAMPLES`): dropped samples would break the sample-index/score-time anchors. Each beat is analysed with Hann-windowed Goertzel filters on its pitches' harmonics, after `configured_latency_secs` + the user's extra latency, searching ±tolerance. Rules: power share above a strictness threshold, beat semitone neighbors, and (single notes only) the pitches a fourth/fifth away; chords skip the fourth/fifth check because their implied root out-scores the played notes. Results are `NoteKey -> bool` marks drawn by `tab_view`.
- `shared::tab::tone::guess_tone` maps a track (GM program, name, tuning, palm-mute share) to a factory preset name; `preset_fits_song` finds user presets by `song`/`artist`. `TabPlayerPanel::ui` returns the chosen chain and `gui.rs` loads it like a preset.

### Spotify (`spotify`, `frontend::ui::spotify`, `shared::tab::library`)
- `spotify::SpotifyClient` is a blocking ureq client (worker threads only) using Authorization Code + PKCE with the loopback listener/PKCE helpers from `tone3000::client` (`wait_for_callback`, `new_pkce`, `random_token` are `pub(crate)` for this). Endpoints follow the February 2026 Web API changes (`/playlists/{id}/items`, `item` field). 401 refreshes once, 429 honors `Retry-After` (capped), 5xx retries twice.
- `SpotifyPanel` (the "🎧 Spotify" page) lists playlists/tracks, sends play/pause/skip to the user's Spotify Connect device and polls `/me/player` every 5 s while visible. It returns `SpotifyAction::OpenTab`, which `gui.rs` passes to `TabPlayerPanel::open_tab`.
- Tabs come only from the user's files: `shared::tab::library` scans `AppSettings::tab_library_dir` and matches by file name (`LibraryIndex::best_match`); manual links are `AppSettings::spotify_tab_links` (track ID -> path).
- Spotify Developer Policy constraints shape the design: no syncing the tab cursor or synth to Spotify playback, no mixing Spotify audio with other audio, no analysing Spotify content, no combining with other services' content (so no tab downloads), show cover art + metadata + links back to Spotify, and delete account data on disconnect. Check the policy before adding Spotify features.

### Transcription and tab repository (`transcribe`, `shared::tab::{export, repository}`, `frontend::ui::transcribe`)
- `transcribe::run(&Request, progress, cancel)` is the blocking pipeline (worker threads only): decode + SHA-256 -> optional separation (`separation::find_separator`: BS-RoFormer SW via `<data dir>/guitar_virtual_amp/tools/msst-venv` + `tools/models/bs_roformer_sw/`, installed by `scripts/install_bs_roformer.sh` and run through `msst-venv/separate_msst.py`, preferred when present; else the external `demucs` CLI found via `GVA_DEMUCS`, `tools/demucs-venv`, or `PATH`, from `scripts/install_demucs.sh`; `GVA_SEPARATOR=demucs|bs-roformer` forces one, and a forced one that isn't installed means no separation. Rust decodes and resamples the song into a 44.1 kHz stereo WAV for BS-RoFormer; both retry on the CPU after a CUDA out-of-memory error; the sidecar `separation` field records which one ran. The BS-RoFormer checkpoint has no stated license: local use only, never bundle it) -> rhythm (`track_rhythm`) -> guitar parts (`transcribe_guitars`: notes per pan part + techniques) and bass notes (`transcribe_stem`) -> `arrange` -> `repository::save`.
- Guitar parts (`transcribe_guitars`, `stereo`): with either separator, the stereo guitar stem (`audio_file::decode_file_stereo`) is split by pan into left/center/right soft-masked STFT parts (ADRess-style, 2048/512, center |pan| < 0.2, side > 0.5). Parts with >= 12% of the energy are transcribed separately; a part whose notes agree with a louder one (`agreement`: note F1 >= 0.5, best over echo lags up to 0.8 s) is the same guitar and dropped, as are parts with < 1/10 of the most notes. The rest become tracks, most-chorded first ("Guitarra base", "Guitarra solo"); `TrackInfo::stem` says which side. Without separation, or mono input, or `GVA_SPLIT_GUITARS=0`, there is one guitar track as before. `Output::guitar_notes`/`guitar_techniques` are the first part's.
- Techniques (`techniques`, `GVA_TECHNIQUES=0` turns them off): rules on Basic Pitch's contour output (output 2, 264 bins, 3 per semitone; MIDI `p` peaks at bin `3 * (p - 21) + 1`, measured). With the CRNN engine, Basic Pitch runs again on the guitar audio just for the contour (`Stage::Techniques`). Single-note passages only: split bends are merged back into one note (glide >= 30 ms, not stepping through semitones), bends/releases and vibrato (3.5-9 Hz, >= 0.25 semitone, 2+ cycles) inside a note, slides (stepped, downward or > 3 semitones glides; gap up to 120 ms) and hammer-ons/pull-offs (jump within 40 ms and no high-frequency pick burst, `PICK_ATTACK`). `arrange` keeps them per pitch on `GridEvent::techniques`; `fret_events_with` penalizes a linked note changing strings (`LINK_STRING_CHANGE`) and bent open strings (`BENT_OPEN_STRING`); `build_track` sets `TabNote` `bend`/`bend_value` (quarter tones)/`bend_release` on the struck piece, `slide`/`hammer` on the last tied piece, `vibrato` on all. `export` writes GP5 bends (Bend or BendRelease points) and shift slides; `import` reads `bend_value`/`bend_release` back. No palm mute or harmonics yet. GuitarSet has almost no bends, so these rules are only checked on synthetic tones (`techniques` tests) and counted on GuitarSet; `eval_real` measures them on real tabs when there are GP8 files.
- Optional models live in `<data dir>/guitar_virtual_amp/tools/models/` (`scripts/install_transcription_models.sh`; `transcribe::installed_models()`): `guitar_gaps_crnn.onnx` (Kong-style high-resolution CRNN with the GAPS guitar weights of Riley et al., exported by `scripts/export_guitar_crnn.py`; `GVA_GUITAR_MODEL` overrides the path, `GVA_GUITAR_ENGINE=basic-pitch` forces the fallback) and `beat_this_small0.onnx` + `beat_this_logmel.onnx` (Beat This!; `GVA_BEAT_MODEL_DIR`). Without them the pipeline falls back to Basic Pitch and the DSP tracker.
- `guitar_electric_crnn.onnx` in the models folder (a local copy of the electric fine-tune; EGDB has no license, so it is never downloaded or bundled) makes the Transcribe form offer GAPS vs electric (`AppSettings::transcription_guitar_model`, `guitar_crnn::GuitarModel`, GAPS by default) and the batch CLI accept `--guitar-model electric`. `GVA_GUITAR_MODEL` still overrides both and is recorded as a custom model. Beat This! uses `beat_this_final0.onnx` when present, else small0 (`beat_net::find_models` returns `BeatModels` with the engine name).
- Rhythm: `beat_net` (Beat This! on the mix, 50 fps logits in 30 s chunks; peaks, then `regularize` fills missed beats and drops doubled ones; `decode_downbeats` is a bar-pointer Viterbi over bars of 2-7 beats with per-meter costs (`METERS`, 4/4 favored) and `METER_CHANGE` per change, scoring downbeat probabilities against their song mean, so the meter can change bar to bar) or `beats` (spectral flux, autocorrelation tempo with a 120 BPM prior, Ellis DP beats, low-band downbeat phase, 4/4 only via `regular_downbeats`; on the drum stem when there is one). `beats::bar_grid` turns beats + downbeat indices into whole bars around the notes: `(times, bar lengths)`, extended with bars like the first/last. `arrange::BeatGrid { times, bar_beats }` carries one length per bar (`BeatGrid::uniform` for fixed meters); `build_bars` writes each bar's numerator.
- Notes: guitar with `guitar_crnn` (16 kHz, 10 s windows with 50% overlap run in parallel by `parallel_map`, Kong's regression post-processing: onset/offset peaks with sub-frame shift, frame threshold, notes < 30 ms dropped) or Basic Pitch; bass always Basic Pitch (`basic_pitch`, ONNX bundled with `include_bytes!`; output 0 = onsets, 1 = notes; frames are 256 samples apart inside each window). `prune_weak` drops weak simultaneous detections (and, for Basic Pitch, overtones). Every model runs through `tract-onnx` 0.23.
- `arrange`: `BeatGrid` (beat times + beats per bar) -> `quantize` (chords = onsets within 35 ms; `choose_subdivisions` picks 16ths or 8th triplets per beat by Viterbi with a straight-time prior; positions are ticks, 960 per beat) -> `fret_events` (Viterbi over fingerings: `FingeringCosts` for stretch, position, high frets, open strings, muted strings inside chords and hand moves, with the hand position carried through open strings, plus the `StringPrior` learned from GuitarSet players 00-02; weights fitted with `eval_fingering`) -> `build_track` (`notate`: tuplets only inside partly used triplet beats, ties for long notes) -> `build_score` (one tempo per bar, numerator = beats per bar).
- The repository is GP5 files (`export::score_to_gp5`, through the `guitarpro` crate's legacy writer; tempos are rounded per bar) plus `.gvtab.json` sidecars (`TabMetadata`): audio hash (dedup/replace), engines, `bar_audio_secs`. `TabPlayerPanel` reads the sidecar on load and plays the source audio with `TabMetadata::sync_map` (exact per-bar sync regardless of GP5 tempo rounding).
- `transcribe::youtube` wraps the external `yt-dlp` (found via `GVA_YTDLP`, `<data dir>/guitar_virtual_amp/tools/ytdlp-venv`, or `PATH`; `scripts/install_ytdlp.sh`): `search` (`ytsearchN:` flat JSON, no API key), `video_info`, `rank` (title/artist words, " - Topic" channels, penalties for live/cover/karaoke..., Spotify duration), `download_audio` (m4a into `youtube_audio/`, reused). Video IDs are validated (11 chars `[A-Za-z0-9_-]`) before reaching the command line; no shell is involved. `transcribe::run_youtube` = download (first 15% of progress) + `run`, recording `source.youtube_id` in the sidecar (`repository::find_by_youtube_id` skips repeats).
- `tract` crates are built with `opt-level = 3` in dev (root `Cargo.toml`), otherwise debug-mode transcription is minutes long.
- Quality benchmarks are ignored tests in `transcribe/eval.rs`: `eval_guitarset` (GuitarSet; prints the final tab F1, the raw model F1, octave errors split up/down, and technique counts against glides in the annotated pitch contours; `GVA_EVAL_TONE="<factory preset>"` plays every recording through that preset's pedal chain first, e.g. "Blues Crunch", "Metal High Gain"), `eval_transcription` (SoundFont renders of GP files), `eval_fingering` (true notes through `fret_events`, compared with the human strings; `GVA_FIT_FINGERING=1` refits the weights), `eval_real` (GP8 files with embedded audio + sync points in `GVA_EVAL_REAL`: F1 vs the best guitar track, all-guitars recall, octave errors, bar lines and meters, technique precision/recall), `eval_guitar_pairs` (GuitarSet comp + solo mixed L/R or L/C, plus one guitar half-panned or with an echo, through the installed separator (`GVA_SEPARATOR` picks one): tracks out and F1 per part; compare with `GVA_SPLIT_GUITARS=0`), `eval_manifest` (any labelled recordings listed in a TSV, `GVA_EVAL_MANIFEST`; written by `scripts/train/prepare_data.py` and `make_mixes.py`: EGDB, Guitar-TECHS, IDMT, GOAT, MUSDB18 band mixes; per-note technique scores when the notes file has a 5th column). `GVA_EVAL_PLAYERS=03,04,05` limits `eval_guitarset` to players a fine-tuned model never saw. `GVA_EVAL_GUITAR_MODEL=electric` runs the electric fine-tune in every benchmark.
- Training (`scripts/train/`, see its README): `render_tones` (desktop bin, through `backend::offline::render`) renders DI through factory presets; `prepare_data.py` -> `align_labels.py` (constant per-recording label shift) -> `finetune_crnn.py` (fp32/TF32, BatchNorm frozen, exports ONNX). Load a trained model with `GVA_GUITAR_MODEL`, or copy it to the models folder as `guitar_electric_crnn.onnx` for the GAPS/electric choice; Beat This! is still found in the models folder (`guitar_crnn::models_dir`). Datasets live outside the repo; GOAT, IDMT and MUSDB18 are non-commercial, so models trained on them can't ship. Demucs retries on the CPU when CUDA runs out of memory (`separation::run_demucs`). Bend thresholds can be swept with `GVA_BEND_RISE`/`GVA_BEND_START`/`GVA_BEND_GLIDE`. `GVA_EVAL_CACHE=<dir>` caches each stem's notes so benchmarks of the later stages skip the models. Run them before and after changing thresholds or the arrangement logic. GuitarSet players 03-05 are the held-out set for fingering: don't fit anything on them.
- Real-song benchmark (`scripts/train/align_tabs.py`, `gp_tabs.py`, `validate_tab_align.py`; workflow in `scripts/train/README.md`): aligns the user's own GP tab to their recording (synctoolbox MrMsDTW on the tab's notes), writes notes files + manifests and a hand-check copy of the tab with a `.gvtab.json` sidecar for the Tabs page (`guitar_core/examples/tab_sync_check.rs` checks it through the app's loader). Only pairs marked `checked` in its checklist go into `eval_real.tsv`.
- Learned fingering (`transcribe::fingering_net`, trained by `scripts/train/fingering/`): a 0.57M-parameter Transformer tagger scores the 6 strings per note (inputs: the fret on each string + 16 timing/interval features, `common.features`), then a decoder puts each chord on distinct strings with a stretch cost and runs a hand-position Viterbi, plus the Viterbi's technique rules. Used for 6-string guitars when `fingering_tagger.onnx` is in the models folder (or `GVA_FINGERING_MODEL`) and `Request::fingering` is `Learned` (`AppSettings::transcription_fingering`, CLI `--fingering`, `GVA_EVAL_FINGERING=learned` in benchmarks, which default to the Viterbi); otherwise, and on any model error, `arrange::fret_events`. It reads each note's transcribed onset/end from `GridEvent::timing`. The Rust port must stay identical to `common.py` (`examples/fingering.rs --learned` + a parity script agreed on 99.94% of 41k true notes). Local file only (trained on EGDB). Pick its settings with `--val-player`, never on GuitarSet 03-05.

### Tone from a recording (`tone`, research, not wired to the UI)
- Design and literature: `docs/papers/tone-estimation/` (Section 10). `tone::estimate(target, dry, &Options)` fits the app's own chain to a target (48 kHz mono, e.g. a separated guitar stem) by analysis by synthesis: the factory presets are the baseline, then one CMA-ES run per amp voicing (`cmaes`: separable CMA-ES on the unit cube, candidates evaluated in parallel, deterministic `Rng`) over `template::Settings` (input level, compressor, distortion, amp gain, reverb; a pedal whose amount is < 0.04 is left out; the amp tone stack is not searched because it is linear after the clipping) rendered with `backend::offline::render_at` (like `render`, at a chosen input RMS). Blocking and CPU-heavy: worker threads only.
- `features::Target::compare` is the search distance: loudness-normalised log band energies (40 bands at 2048/512 and 20 at 512/128, 60 Hz to 16 kHz), mean absolute dB over the target's active frames *after* adding the centred, ±18 dB-capped difference of the long-term spectra. That EQ allowance lets the search fit gain/compression/drive/reverb while the linear colour (cabinet, pickups, mix EQ) goes to the final matching filter: `matching::ir_from_eq` (minimum-phase IR, 2048 taps, real-cepstrum method) placed in a Cabinet pedal at the end of the chain (`Candidate::chain_with_ir`, `matching::write_ir`). `features::plain_distance` (no EQ allowance) is the benchmark score.
- Without the user's DI, the dry signal is the notes played by `pluck` (extended Karplus-Strong, timing from the transcription or labels, then `pluck::DI_EQ`). `pluck::Model` defaults and `DI_EQ` were fitted on Guitar-TECHS DI with `eval::fit_pluck`; refit them there, never on EGDB (the benchmark).
- Benchmarks (ignored tests in `tone/eval.rs`): `eval_tone` on EGDB (`GVA_TONE_MANIFEST=<prepared>/eval_egdb.tsv`): per item, the DI through a random template chain + random cabinet-like EQ (settings known) and the Marshall/Mesa/Plexi renders (gear outside the chain); scores the true DI rendered through each estimate (dry DI, best factory preset, preset + match, search + match from notes, search + match from the true DI as upper bound). `GVA_TONE_LIMIT`, `GVA_TONE_GENS`, `GVA_TONE_SECS`, `GVA_TONE_ORACLE=0`, `GVA_TONE_OUT=<dir>` (WAVs for listening). `pluck_vs_di` / `fit_pluck` take `GVA_PLUCK_ITEMS=<di.wav>:<notes.txt>,...`.

### Shared config (`guitar_core::shared`)

- `config::GLOBAL_CONFIG` — the single source of truth for sample rate (48000.0 Hz) and buffer sizing constants, referenced by both DSP code (e.g. filter cutoff math) and the audio pipeline.
- `pedals::PedalDescription` — the serializable-by-value description of a pedal + its params, iterated via `strum::EnumIter` to drive the "Add <Pedal>" buttons. `pedals::PedalInstance` wraps it with the bypass flag (`enabled`, defaulting to `true` so old preset files still load); `Vec<PedalInstance>` is the message type sent from the UI thread to the audio thread over `pedal_tx`/`pedal_rx`.

### UI (`guitar_core::frontend`)

- `gui::AudioApp` implements `eframe::App`. Holds the live sample ring (a `VecDeque<f64>`, drained from `audio_rx` each frame) for the oscilloscope, and a `Vec<PedalInstance>` as the UI-side source of truth for the pedal chain — any mutation sends the full vec down `pedal_tx` (see Pedal chain for how the audio thread applies it).
- `frontend::lib::fft::compute_fft` computes the spectrum shown in the FFT plot, driven off the same sample buffer.
- `frontend::ui::pedals::render_pedal_ui` dispatches per-pedal-type slider UI and returns a `PedalAction` (`None`/`Updated`/`Deleted`/`Tone3000`) that `AudioApp::update` uses to know whether to push a chain update, remove the pedal from the vec, or open the TONE3000 window.
- Device selection/refresh in the UI runs on background threads (see Audio pipeline section) to avoid blocking the egui frame loop.

Note: a fair amount of in-code comments and log/print strings are in Portuguese (the primary dev's language) — expect to encounter this reading `capture.rs` and `gui.rs` in particular.
